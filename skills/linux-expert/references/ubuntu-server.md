## Releases and support

Source: https://ubuntu.com/releaseendoflife (checked 2026-10).

| LTS | Standard security maintenance ends | ESM (Ubuntu Pro) ends |
|---|---|---|
| 26.04 LTS | May 2031 | May 2036 |
| 24.04 LTS | May 2029 | May 2034 |
| 22.04 LTS | May 2027 | May 2032 |

- Run LTS releases on servers; interim releases are supported for months only.
- `lsb_release -a` or `cat /etc/os-release` identifies the release; `pro status` shows ESM entitlement; `pro security-status` summarises packages by support source.
- Plan the move off a release at least a year before standard support ends; ESM is a bridge, not a plan.

## Netplan

Netplan reads YAML from `/etc/netplan/*.yaml` and renders configuration for `systemd-networkd` (server default) or NetworkManager. Do not edit `/etc/network/interfaces` or run ad-hoc `ip` commands as the source of truth on a netplan host.

- Keep files `0600` and root-owned (netplan warns about permissive modes); order with numeric prefixes, later files override earlier ones.
- Test remote changes with `sudo netplan try` (rolls back after a timeout unless confirmed); `sudo netplan generate` validates; `sudo netplan apply` applies.
- Inspect with `networkctl status`, `ip -br addr`, `resolvectl status`, `netplan status`.
- Cloud images may carry `/etc/netplan/50-cloud-init.yaml` generated by cloud-init; to own the network config yourself, disable cloud-init networking with a file in `/etc/cloud/cloud.cfg.d/` containing `network: {config: disabled}`.

```yaml
# /etc/netplan/01-bond.yaml  (bonded NICs plus a VLAN; interface names are examples)
network:
  version: 2
  renderer: networkd
  ethernets:
    eno1: {}
    eno2: {}
  bonds:
    bond0:
      interfaces: [eno1, eno2]
      parameters:
        mode: 802.3ad
        lacp-rate: fast
        mii-monitor-interval: 100
  vlans:
    bond0.20:
      id: 20
      link: bond0
      addresses: [10.20.0.10/24]
      routes:
        - to: default
          via: 10.20.0.1
      nameservers:
        addresses: [10.20.0.2, 10.20.0.3]
        search: [example.internal]
```

802.3ad needs a matching LACP configuration on the switch.

## apt and unattended-upgrades

- Third-party repositories: store the vendor key under `/etc/apt/keyrings/` and reference it with `Signed-By:` (deb822 `.sources` files) or `[signed-by=/etc/apt/keyrings/vendor.gpg]`. Never use `apt-key add`, which trusts a key for every repository. Verify the key fingerprint against the vendor's documentation, and do not pipe a download into `sh` without verifying a checksum or signature.
- Ubuntu 24.04 and later use the deb822 format in `/etc/apt/sources.list.d/ubuntu.sources`; older releases use `/etc/apt/sources.list`.
- Pin or hold with `apt-mark hold <pkg>` and preferences files in `/etc/apt/preferences.d/`; list holds with `apt-mark showhold`.
- `needrestart` (installed by default on recent Ubuntu Server) reports services running outdated libraries after upgrades; `checkrestart`-style review belongs in patch runbooks.

Automatic security updates:

```
# /etc/apt/apt.conf.d/20auto-upgrades
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
```

```
// /etc/apt/apt.conf.d/52unattended-upgrades-local  (overrides defaults in 50unattended-upgrades)
Unattended-Upgrade::Allowed-Origins {
        "${distro_id}:${distro_codename}-security";
        "${distro_id}ESMApps:${distro_codename}-apps-security";
        "${distro_id}ESM:${distro_codename}-infra-security";
};
Unattended-Upgrade::Remove-Unused-Dependencies "true";
Unattended-Upgrade::Automatic-Reboot "false";
Unattended-Upgrade::Mail "ops@example.com";
```

- Test the configuration with `sudo unattended-upgrade --dry-run --debug`; logs are in `/var/log/unattended-upgrades/`.
- Automatic reboots (`Automatic-Reboot "true"` with `Automatic-Reboot-Time`) suit stateless nodes behind a load balancer; for stateful hosts schedule reboots, or use Livepatch for kernel fixes.
- The `-updates` pocket is not part of the security-only pattern above; add it only if you accept non-security changes.

## Ubuntu Pro, ESM and Livepatch

Ubuntu Pro adds Expanded Security Maintenance for `main` (esm-infra) and `universe` (esm-apps), Livepatch, FIPS and compliance tooling (CIS via the `usg` tool). Free for personal use on a limited number of machines; check https://ubuntu.com/pro for current terms.

```bash
pro status                      # attachment and service state
sudo pro enable esm-infra
sudo pro enable esm-apps
sudo pro enable livepatch
pro security-status             # what is covered by which source
canonical-livepatch status      # after livepatch is enabled
```

Attaching safely:
- A Pro token is a credential. Do not place it in cloud-init user-data, in a command line (visible in `ps` and shell history), in images, in git or in logs.
- On public clouds prefer Ubuntu Pro images from the marketplace, which attach automatically to a licence from the cloud provider.
- To attach a token on your own images, fetch it at first boot from a secret manager using the instance's role, write it to a root-only file and attach from that file, then remove the file. The boot script itself contains no secret.
- After provisioning, attaching by hand (`sudo pro attach`) or from configuration management that reads from a secret store is also fine.
- `pro attach` accepts an attach-config file in place of a token argument; confirm the option and file format with `pro attach --help` and the current Ubuntu Pro client documentation on your release.

```bash
#!/bin/bash
# /usr/local/sbin/pro-attach.sh  (run once at boot by a systemd oneshot or runcmd; contains no secret)
set -euo pipefail
umask 077
cfg="$(mktemp /run/pro-attach.XXXXXX)"
trap 'shred -u "$cfg" 2>/dev/null || rm -f "$cfg"' EXIT
token="$(aws secretsmanager get-secret-value --secret-id ubuntu-pro-token \
          --query SecretString --output text)"
printf 'token: %s\nenable_services:\n  - esm-infra\n  - livepatch\n' "$token" > "$cfg"
unset token
pro attach --attach-config "$cfg"
```

The instance role needs `secretsmanager:GetSecretValue` on that one secret only. Equivalent patterns exist for other clouds' secret managers.

Compliance: `sudo pro enable usg`, then `sudo usg audit cis_level1_server` (or `cis_level2_server`) and `sudo usg fix <profile>`; review the report and record accepted deviations. Check the `usg` documentation for the profile names available on your release.

## cloud-init

cloud-init runs on first boot from user-data, vendor-data and datasource metadata. Treat user-data as readable by anyone who can query the instance metadata service and as present in logs and on disk (`/var/lib/cloud/instance/user-data.txt`).

- Never put passwords, tokens (including Ubuntu Pro tokens), private keys or API credentials in user-data. Use public SSH keys only, fetch secrets at boot from a secret manager with an instance role, and enforce IMDSv2 (or the cloud equivalent) to limit metadata exposure.
- Validate before shipping: `cloud-init schema --config-file user-data.yaml --annotate`; on a running host `cloud-init status --long`, `cloud-init schema --system`, logs in `/var/log/cloud-init.log` and `/var/log/cloud-init-output.log`.
- Modules run once per instance by default; `cloud-init clean --logs` on a test VM resets state for another run (do not run on production hosts).
- Prefer a small user-data that installs a configuration-management agent or pulls a signed bootstrap, over a large inline script.

```yaml
#cloud-config
# user-data: no secrets. Public key only; password login disabled.
hostname: app-01
manage_etc_hosts: true
users:
  - name: ops
    shell: /bin/bash
    lock_passwd: true
    ssh_authorized_keys:
      - ssh-ed25519 AAAA...example ops@example.com
ssh_pwauth: false
package_update: true
packages: [unattended-upgrades, ufw, fail2ban]
write_files:
  - path: /etc/ssh/sshd_config.d/10-hardening.conf
    permissions: "0644"
    content: |
      PermitRootLogin no
      PasswordAuthentication no
      AuthenticationMethods publickey
runcmd:
  - [ ufw, default, deny, incoming ]
  - [ ufw, allow, OpenSSH ]
  - [ ufw, --force, enable ]
```

The `ops` user above has no sudo rights; add a least-privilege file under `/etc/sudoers.d/` for the commands it needs, validated with `visudo -c`. Do not use `sudo: ALL=(ALL) NOPASSWD:ALL` in cloud-init user config.

## Autoinstall

Autoinstall (subiquity) automates bare-metal and VM installs from a YAML file with a top-level `autoinstall:` key and `version: 1`, supplied by cloud-init NoCloud, an ISO, or a PXE-served location. Check the Ubuntu Server installation documentation for the schema of the release you install.

- Provide `identity` with a hashed password (generate with `mkpasswd -m sha-512`) or, better, disable password login and supply `ssh.authorized-keys` with `ssh.allow-pw: false`.
- Keep the file free of plaintext secrets; serve it over a trusted, access-controlled channel.
- Use `late-commands` sparingly; prefer handing the host to configuration management after first boot.

## AppArmor

AppArmor is enabled by default on Ubuntu and confines programs by path-based profiles in `/etc/apparmor.d/`.

- `sudo aa-status` lists profiles and modes; `sudo aa-complain /etc/apparmor.d/<profile>` logs violations without blocking; `sudo aa-enforce` re-enables blocking; reload a profile with `sudo apparmor_parser -r /etc/apparmor.d/<profile>`.
- Denials appear in `journalctl -k | grep -i apparmor` and `/var/log/syslog`/`auditd` as `apparmor="DENIED"`. Use `aa-logprof` (apparmor-utils) to turn them into rules, then review each addition instead of accepting all.
- Do not disable AppArmor globally to make a service work; put the one profile in complain mode, fix the rules, and re-enforce.
- A service can be confined from its unit with `AppArmorProfile=` (see systemd.exec); snaps and some container runtimes bring their own profiles.

```
# /etc/apparmor.d/usr.local.bin.example-api
#include <tunables/global>

/usr/local/bin/example-api {
  #include <abstractions/base>
  #include <abstractions/nameservice>

  /usr/local/bin/example-api mr,
  /etc/example-api/** r,
  /var/lib/example-api/** rw,
  /var/log/example-api/ rw,
  /var/log/example-api/** rw,

  network inet stream,
  network inet6 stream,

  deny /home/** rwx,
}
```

## ufw and nftables

- ufw is the default front end on Ubuntu; it manages rules through the iptables compatibility layer, which on current Ubuntu uses the nftables kernel backend. Use one tool to own the firewall: ufw or hand-written nftables (`/etc/nftables.conf` with `nftables.service`), not both.
- Baseline: `sudo ufw default deny incoming`, `sudo ufw default allow outgoing`, `sudo ufw allow OpenSSH` (or `sudo ufw limit OpenSSH` for connection rate limiting), then `sudo ufw enable`. Allow the SSH rule before enabling on a remote host.
- Scope rules: `sudo ufw allow from 10.0.0.0/8 to any port 5432 proto tcp`. List with `sudo ufw status numbered`; delete by number.
- Docker publishes ports through its own iptables chains and bypasses ufw rules; control exposure by binding published ports to `127.0.0.1` or an internal address, or manage Docker's `DOCKER-USER` chain (see docker-expert).
- Inspect the effective ruleset with `sudo nft list ruleset`.

## Upgrades and snaps

- Release upgrades: `sudo do-release-upgrade` from one LTS to the next, after a snapshot or backup and a rehearsal on a clone; run it in a terminal multiplexer, and expect third-party repositories to be disabled and to need review afterwards. Read the current upgrade documentation for when the next LTS is offered.
- Snaps refresh automatically. Control timing with `sudo snap refresh --hold`, `snap set system refresh.timer=...` or `refresh.hold`; check `snap refresh --time`. Pin production-critical snaps to a tested channel.
- Kernel updates need a reboot unless Livepatch covers the CVE; `/var/run/reboot-required` signals a pending reboot.
