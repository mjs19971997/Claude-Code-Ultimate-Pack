# Supply Chain, OIDC and Delivery

Reference for provenance, attestations, signing, pinning, keyless cloud authentication and progressive delivery in GitHub-based pipelines. Verified against SLSA specification v1.2, actions/attest v4.2.2, GitHub CLI 2.103.x (`gh attestation`), cosign 3.1.x, syft 1.55.x, zizmor 1.31.x, actionlint 1.7.x, pinact 5.0.x and Argo Rollouts 1.10.x (2026-10). Artifact attestations are available for public repositories on all current plans; private and internal repositories need GitHub Enterprise Cloud, and GitHub Enterprise Server is not supported.

## 1. What to defend

| Threat | Control |
|---|---|
| Compromised third-party action or tag moved | Pin full commit SHAs, workflow dependency lockfile, Dependabot with cooldown, allow-lists |
| Malicious dependency or typosquat | Lockfiles, dependency review on pull requests, cooldown before adopting new releases, install scripts disabled where possible |
| Stolen long-lived credential | OIDC short-lived tokens, environment-scoped secrets, secret scanning with push protection |
| Tampered artifact between build and deploy | Attestation or signature verified at deploy, deploy by digest |
| Build system compromise | Ephemeral hosted runners, least-privilege tokens, isolated reusable-workflow builds |
| Poisoned cache or artifact from untrusted PR | Read-only caches on low-trust triggers, no execution of fork artifacts in privileged workflows |
| Unreviewed pipeline change | CODEOWNERS and rulesets on `.github/workflows` |

## 2. SLSA build track

SLSA v1.2 describes build integrity levels:
- **Build L1**: provenance exists (who built what, from which source and build steps).
- **Build L2**: provenance is signed and generated by a hosted build platform, so it cannot be forged by the build's users after the fact.
- **Build L3**: the platform isolates builds from each other and from the signing material, so a compromised build cannot forge provenance.

Generating attestations with `actions/attest` on GitHub-hosted runners yields signed provenance (L2); GitHub documents a pattern that reaches L3 by building inside a reusable workflow and verifying the signer workflow identity. Check the current GitHub guide "Using artifact attestations and reusable workflows to achieve SLSA v1 Build Level 3" for the exact steps. The slsa-github-generator project (v2.1.0) provides an alternative that builds provenance in a separate trusted workflow; verify with `slsa-verifier`.

## 3. Artifact attestations on GitHub

Create (permissions: `id-token: write`, `attestations: write`, `artifact-metadata: write`, plus `contents: read`):

```yaml
- uses: actions/attest@1e69f48acb82d1966a394da916b4c1698aa569d6 # v4.2.2
  with:
    subject-path: dist/*.tgz            # or subject-digest + subject-name for images, or subject-checksums
```

- Modes by inputs: none of the predicate inputs = SLSA build provenance; `sbom-path` = SBOM attestation (SPDX or CycloneDX JSON up to 16 MB); `predicate-type` with `predicate` or `predicate-path` = custom attestation.
- For container images use `subject-name` (image name without tag) and `subject-digest` (`sha256:...`); add `push-to-registry: true` to store the attestation next to the image.
- `actions/attest-build-provenance` is a thin wrapper around `actions/attest` since its v4; new workflows use `actions/attest`.

Verify before deploy (consumer side):

```bash
gh attestation verify app.tgz --repo example-org/app
gh attestation verify app.tgz --owner example-org --signer-workflow example-org/app/.github/workflows/release.yml
gh attestation verify oci://ghcr.io/example-org/app@sha256:<digest> --repo example-org/app
gh attestation verify app.tgz --repo example-org/app --predicate-type <predicate-type-of-the-sbom-attestation> --format json
gh attestation download app.tgz --repo example-org/app      # save the bundle for offline use
gh attestation trusted-root > trusted_root.jsonl             # offline verification roots
```

- The default predicate type is SLSA provenance (`https://slsa.dev/provenance/v1`); pass `--predicate-type` for SBOM or custom attestations.
- Verification requires `--owner` or `--repo`; narrowing to `--signer-workflow` pins which workflow produced it, which matters when many repositories in an organization can attest.
- Use `--bundle` with an attestation file to verify without network access to the attestation API.
- In Kubernetes, enforce verification at admission with a policy controller (for example the sigstore policy-controller or Kyverno image verification) configured for the GitHub OIDC issuer and your workflow identity (kubernetes-expert).

## 4. SBOMs

- `docker buildx build --sbom=true` (or `sbom: true` in build-push-action) attaches an SBOM attestation to the image.
- Generate for directories and archives with syft: `syft dir:. -o spdx-json=sbom.spdx.json` or `syft app.tgz -o cyclonedx-json=sbom.cdx.json`, then attest with `actions/attest` `sbom-path`.
- The dependency graph can export an SPDX SBOM: `gh api repos/{owner}/{repo}/dependency-graph/sbom`.
- Store SBOMs with releases; scan them in CI for known vulnerabilities and license policy.

## 5. Image signing with cosign

Keyless signing uses the workflow's OIDC identity and Sigstore:

```yaml
permissions:
  contents: read
  id-token: write
  packages: write
steps:
  - uses: sigstore/cosign-installer@<full-sha>   # v4.1.0 at time of writing; installs cosign 3.x
  - name: Sign image by digest
    env:
      IMAGE: ghcr.io/example-org/app
      DIGEST: ${{ steps.build.outputs.digest }}
    run: cosign sign --yes "${IMAGE}@${DIGEST}"
```

Verify at deploy:

```bash
cosign verify ghcr.io/example-org/app@sha256:<digest> \
  --certificate-identity "https://github.com/example-org/app/.github/workflows/release.yml@refs/tags/v1.4.0" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Use `--certificate-identity-regexp` for tag patterns. Always sign and verify by digest, never by mutable tag. Cosign 3.x changed some bundle and storage defaults; check the release notes for flags before upgrading scripts. GitHub attestations and cosign signatures are alternatives; pick one verification path per consumer.

## 6. Pinning, lockfiles and linting

- Pin: `uses: owner/repo@<40-hex-sha> # v1.2.3`. Tools: Dependabot (understands the version comment), pinact (`pinact run` rewrites tags to SHAs), Renovate.
- Workflow dependency lockfile (github.com plans): `gh extension install github/gh-actions-lock`, then `gh actions-lock` writes `.github/workflows/actions.lock` with commit SHAs and repository IDs for every action including transitive ones; it does not pin `jobs.<id>.uses` reusable workflow calls, which still need SHAs. Organization policy can require it. Do not edit the file by hand.
- Dependabot for actions: `package-ecosystem: github-actions`, `directory: /`, weekly, `cooldown` to delay brand-new releases, `groups` to batch minor updates. Dependabot alerts only cover actions that use semantic versions.
- Lint in CI: `actionlint` for syntax and types, `zizmor` for security findings (template injection, excessive permissions, unpinned uses, dangerous triggers), OpenSSF Scorecard for repository posture.
- Audit the source of actions you adopt: what they read, where they send data, which tokens they use.

## 7. Dependencies and publishing

- Install from lockfiles only: `npm ci`, `pip install --require-hashes -r requirements.txt`, `go mod verify`, `cargo build --locked`. Fail CI if the lockfile changes.
- Dependency review action on pull requests; Dependabot alerts and security updates on.
- Treat install scripts as code execution: `npm ci --ignore-scripts` for jobs that do not need them, and verify provenance where registries support it (`npm audit signatures`).
- Publish packages with registry trusted publishing (OIDC) instead of long-lived tokens where supported (for example npm, PyPI, RubyGems, crates.io); the job needs `id-token: write`, and the registry is configured with the repository and workflow that may publish. Check each registry's current documentation.
- Generate provenance for published packages (npm `--provenance`, PyPI attestations) when the registry supports it.

## 8. OIDC to cloud providers

Claims in the GitHub OIDC token include `iss` (`https://token.actions.githubusercontent.com`), `aud`, `sub`, `repository`, `repository_owner`, `ref`, `environment`, `workflow_ref`, `job_workflow_ref` and `runner_environment`. Default `sub` values:
- `repo:ORG/REPO:ref:refs/heads/main` for branch runs without an environment,
- `repo:ORG/REPO:environment:production` when the job uses an environment (the environment replaces the ref),
- `repo:ORG/REPO:pull_request` for pull request events.

Principles: trust only the specific repository and environment (or branch or tag); use a separate role for plan and apply; require the environment gate for production; keep session lifetimes short; never use wildcard `sub` such as `repo:ORG/*` for production roles. Organizations can customize the `sub` claim template (for example include `job_workflow_ref` to bind the identity to a reusable workflow).

AWS (trust policy in aws-expert, `references/iam-and-security.md`):

```yaml
permissions:
  id-token: write
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@e1253824e5c10ff9df46874f81ed3ec929e19cfd # v6.3.0
    with:
      role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
      aws-region: ${{ vars.AWS_REGION }}
```

Azure: create a Microsoft Entra application (or user-assigned managed identity) with a federated credential whose subject is `repo:ORG/REPO:environment:production`, issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`; the workflow uses `azure/login` with `client-id`, `tenant-id` and `subscription-id` (identifiers, not secrets) and `id-token: write`.

Google Cloud: create a workload identity pool and OIDC provider with an attribute condition such as `assertion.repository == 'ORG/REPO' && assertion.ref == 'refs/heads/main'`; grant the service account `roles/iam.workloadIdentityUser` to the principal for that repository; use `google-github-actions/auth` with `workload_identity_provider` and `service_account`.

Pin all three actions by SHA like any other third-party action.

## 9. Delivery strategies

| Strategy | When | Mechanics | Rollback |
|---|---|---|---|
| Rolling | Stateless service, backward-compatible change | Replace instances gradually with health checks | Redeploy previous digest |
| Blue/green | Need instant cutover and rollback | Stand up the new version beside the old, switch traffic at the load balancer or service, keep old for a window | Switch back |
| Canary | Risky change, measurable SLIs | Send 1 to 10 percent, analyze error rate and latency, increase in steps | Automatic abort to 0 percent |
| Feature flag | Decouple deploy from release | Ship dark, enable per cohort | Turn flag off |
| Recreate | Stateful singleton, downtime acceptable | Stop old, start new | Redeploy |

Database changes use expand, migrate, contract: add compatible schema first, deploy code that works with both, backfill, then remove the old schema in a later release. Migrations run as a separate, idempotent job before the app rollout and are reviewed like code.

Argo Rollouts canary with analysis (Kubernetes details in kubernetes-expert; the image is deployed by digest):

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: api
spec:
  replicas: 5
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
        - name: api
          image: ghcr.io/example-org/app@sha256:<digest>
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: { duration: 5m }
        - analysis:
            templates:
              - templateName: error-rate
        - setWeight: 50
        - pause: { duration: 10m }
```

Gate promotion on measured signals (HTTP 5xx rate, latency percentile, saturation) and keep manual abort available. Track delivery with the four DORA metrics (deployment frequency, lead time, change failure rate, time to restore).

## 10. Responding to a compromised action or secret

1. Disable or restrict workflows that use the action; pin to a known-good SHA or remove it.
2. Find every use across the organization with code search (`org:example-org "owner/action@"`).
3. Rotate every secret the affected jobs could read; revoke OIDC-assumable role sessions by tightening the trust policy temporarily.
4. Review run logs and cloud audit logs (CloudTrail, Entra sign-in logs, Cloud Audit Logs) for the period for unexpected activity.
5. Re-run builds from a clean state, re-attest, and redeploy verified artifacts.
6. Add the missing control afterwards (pinning, permissions, allow-list, egress filtering) and record it in the incident review.
