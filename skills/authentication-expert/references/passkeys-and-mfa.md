# Passkeys, WebAuthn and MFA

This file covers WebAuthn registration and authentication with `@simplewebauthn/server` (v14; browser side `@simplewebauthn/browser`), passkey rollout decisions, TOTP with `otplib` (v13), backup codes and step-up policy. WebAuthn Level 3 is the current specification level; check the W3C page for its status and for individual features.

## 1. Concepts

- A passkey is a WebAuthn credential bound to an RP ID (your registrable domain) so a phishing site on another domain cannot use it. The server stores the credential id, public key, signature counter, transports and backup flags; the private key never leaves the authenticator.
- Discoverable credentials (`residentKey: 'required'`) allow username-less login. `userVerification: 'preferred'` or `'required'` controls PIN or biometric checks; use `'required'` when the passkey is the only factor.
- Synced passkeys (backup eligible and backed up flags) improve recovery but mean the credential's security is tied to the sync provider account. Device-bound security keys offer stronger attestation for high-assurance populations.
- Attestation: `'none'` is right for consumer apps. Request `'direct'` or `'enterprise'` only when policy needs to restrict authenticator models, and then verify against the FIDO Metadata Service data.
- The signature counter may stay at 0 for synced passkeys; reject only when a non-zero stored counter fails to increase.

## 2. Registration and authentication ceremonies

```typescript
import {
  generateRegistrationOptions, verifyRegistrationResponse,
  generateAuthenticationOptions, verifyAuthenticationResponse,
  type WebAuthnCredential, type RegistrationResponseJSON, type AuthenticationResponseJSON,
} from '@simplewebauthn/server';

const rpName = 'Example App';
const rpID = 'example.com';                         // registrable domain, no scheme or port
const expectedOrigin = ['https://app.example.com']; // exact origins that may run the ceremony

interface Stored extends WebAuthnCredential { userId: string; deviceType: string; backedUp: boolean }
declare const challenges: { put(key: string, c: string, ttlMs: number): Promise<void>; take(key: string): Promise<string | undefined> };
declare const creds: {
  listByUser(userId: string): Promise<Stored[]>;
  get(credentialId: string): Promise<Stored | undefined>;
  insert(c: Stored): Promise<void>;
  updateCounter(id: string, counter: number, backedUp: boolean): Promise<void>;
};

export async function registrationStart(userId: string, userName: string) {
  const existing = await creds.listByUser(userId);
  const options = await generateRegistrationOptions({       // async since v10
    rpName, rpID, userName,
    userID: new TextEncoder().encode(userId),                // opaque handle, not an email
    attestationType: 'none',
    excludeCredentials: existing.map((c) => ({ id: c.id, transports: c.transports })),
    authenticatorSelection: { residentKey: 'required', userVerification: 'preferred' },
  });
  await challenges.put(`reg:${userId}`, options.challenge, 5 * 60_000);
  return options;
}

export async function registrationFinish(userId: string, response: RegistrationResponseJSON) {
  const expectedChallenge = await challenges.take(`reg:${userId}`);  // single use
  if (!expectedChallenge) throw new Error('challenge expired');
  const v = await verifyRegistrationResponse({ response, expectedChallenge, expectedOrigin, expectedRPID: rpID });
  if (!v.verified) throw new Error('registration failed');
  const { credential, credentialDeviceType, credentialBackedUp } = v.registrationInfo;
  await creds.insert({ ...credential, userId, deviceType: credentialDeviceType, backedUp: credentialBackedUp });
}

export async function authenticationStart(sessionKey: string) {
  const options = await generateAuthenticationOptions({ rpID, userVerification: 'preferred' }); // empty allowCredentials: discoverable
  await challenges.put(`auth:${sessionKey}`, options.challenge, 5 * 60_000);
  return options;
}

export async function authenticationFinish(sessionKey: string, response: AuthenticationResponseJSON) {
  const expectedChallenge = await challenges.take(`auth:${sessionKey}`);
  const credential = await creds.get(response.id);
  if (!expectedChallenge || !credential) throw new Error('authentication failed');
  const v = await verifyAuthenticationResponse({ response, expectedChallenge, expectedOrigin, expectedRPID: rpID, credential });
  if (!v.verified) throw new Error('authentication failed');
  await creds.updateCounter(credential.id, v.authenticationInfo.newCounter, v.authenticationInfo.credentialBackedUp);
  return credential.userId;                                   // establish the session after regenerate()
}
```

Server rules: challenges are generated by the library, stored server-side with a short TTL and consumed exactly once; `expectedOrigin` and `expectedRPID` are fixed configuration, never derived from request headers; the session id is regenerated after a successful authentication; registering a new passkey requires an authenticated session (and step-up for existing accounts). `generateRegistrationOptions` and `generateAuthenticationOptions` are async in current versions, and `userID` is a `Uint8Array`.

Browser side, with `@simplewebauthn/browser`: `startRegistration({ optionsJSON })` and `startAuthentication({ optionsJSON })` take the options JSON from the server and return the response to post back. Use conditional UI (`useBrowserAutofill: true` on `startAuthentication`) to offer passkeys in the username field autofill; check the library docs for the exact current signature.

## 3. Rolling out passkeys

1. Offer "Add a passkey" after a password login; treat it as an additional credential.
2. Prompt on later logins, track adoption and failures.
3. Allow removal of passwords only when users have at least two passkeys or a verified recovery path.
4. Related origins (WebAuthn Level 3) allow one passkey across several of your own domains; configure the `/.well-known/webauthn` document per the specification and keep the list short.
5. Native apps use the platform passkey APIs with an associated-domains or Digital Asset Links relationship to the RP ID.

## 4. TOTP (RFC 6238)

TOTP is phishable and relies on a shared secret, so rank it below passkeys, but it remains the common fallback.

```typescript
import { generateSecret, generateURI, verify } from 'otplib';
import { timingSafeEqual, createHash } from 'node:crypto';

declare const mfa: {
  getSecret(userId: string): Promise<{ secret: string; lastTimeStep: number | null } | undefined>; // secret encrypted at rest
  setLastTimeStep(userId: string, step: number): Promise<void>;
};

export const enroll = (email: string) => {
  const secret = generateSecret();                // base32, 160 bits
  return { secret, uri: generateURI({ issuer: 'Example App', label: email, secret }) };
};

export async function verifyTotp(userId: string, token: string): Promise<boolean> {
  const rec = await mfa.getSecret(userId);
  if (!rec || !/^\d{6}$/.test(token)) return false;
  const r = await verify({
    strategy: 'totp', secret: rec.secret, token,
    epochTolerance: [30, 0],                       // allow the previous step only
    ...(rec.lastTimeStep !== null && { afterTimeStep: rec.lastTimeStep }), // a code works once
  });
  if (!r.valid || !('timeStep' in r)) return false;
  await mfa.setLastTimeStep(userId, r.timeStep);
  return true;
}

// Backup codes: random, stored as SHA-256 (high-entropy values need no slow hash), compared in constant time.
export const hashCode = (c: string) => createHash('sha256').update(c).digest();
export const codeMatches = (input: string, stored: Buffer) => timingSafeEqual(hashCode(input), stored);
```

- Enrol: show the `otpauth://` URI as a QR code and the base32 secret as text; activate the factor only after the user submits one valid code.
- Store the secret encrypted at rest (envelope encryption with a key outside the database).
- Accept the current and previous step only, reject reuse of a time step, and rate-limit verification (6 digits are guessable under unlimited attempts).
- Defaults of 6 digits, 30 seconds and SHA-1 are what most authenticator apps support; do not change them without testing the apps you target.

## 5. Backup codes and other factors

- Generate 8 to 10 random codes (at least 64 bits each), show them once, store SHA-256 hashes, consume on use, and let the user regenerate (which invalidates the old set).
- SMS and voice codes are the weakest factor (SIM swap, interception, social engineering); allow them only as a low-tier fallback, never as the only recovery for high-value accounts. Email codes are no stronger than the mailbox.
- Push-approval factors need number matching and rate limiting to resist fatigue attacks.

## 6. Step-up and assurance

- Store `authTime` and `amr` (for example `['pwd', 'hwk']`) in the session or token. Sensitive actions require authentication within N minutes with a factor of the required strength; if not, redirect to a re-authentication ceremony and then return.
- OIDC providers express this with `acr_values` and `max_age`; send `max_age` (and `acr_values`) as authorization request parameters, and pass `maxAge` in the `authorizationCodeGrant` checks so `openid-client` verifies `auth_time` in the id_token.
- Adding or removing a factor, changing email, and exporting data are step-up actions; notify the user after each.

## 7. Tests

- Registration with a wrong origin, wrong RP ID, expired or reused challenge fails.
- Authentication for an unknown credential id fails with the same error as a bad signature.
- Counter rollback (when the stored counter is non-zero) is rejected and flagged.
- Same TOTP code accepted once only; backup code works once and then fails.
- Removing the last strong factor is blocked unless a recovery path is verified.
