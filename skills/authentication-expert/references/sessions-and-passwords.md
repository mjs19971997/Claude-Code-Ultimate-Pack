# Sessions, Passwords and Recovery

This file covers server-side sessions, cookie settings, password policy and storage details, breached-password checks, reset and recovery flows, and rate limiting for login. The core Argon2id and session login examples are in SKILL.md (Examples 1 and 2); the OAuth side is in [oauth2-oidc.md](oauth2-oidc.md).

## 1. Cookie sessions

- Cookie: `__Host-sid; HttpOnly; Secure; SameSite=Lax; Path=/`, no `Domain`. The `__Host-` prefix makes browsers refuse the cookie unless it is `Secure`, has `Path=/` and no `Domain`, which stops sibling subdomains from planting or overwriting it. Use `SameSite=Strict` when users never arrive via cross-site links into authenticated pages.
- The cookie holds only a random session id (at least 128 bits, from the framework or `crypto.randomBytes`); all state lives server-side (Redis or a SQL table). Signed cookies with data inside are a different design (stateless sessions) with JWT-like revocation problems.
- Lifecycle: regenerate the id on login, privilege change and MFA success; idle timeout (15 to 30 minutes for sensitive apps, longer for low-risk ones) and an absolute lifetime (hours to days); destroy on logout; store `userId`, `authTime`, `amr` (methods used) and a `sessionVersion` that password change increments.
- "Sign out everywhere": keep a per-user set of session ids, or compare `sessionVersion`, so the server can revoke without waiting for expiry.
- Show active sessions (device, approximate location, last use) and let users revoke them.
- Do not put session ids in URLs. Do not accept a session id the server did not issue (strict mode), which prevents fixation by cookie injection.

CSRF for cookie-authenticated requests: `SameSite=Lax` blocks cross-site POSTs in current browsers but is not enough alone (same-site subdomain attacks, legacy clients). Add `Origin` or `Sec-Fetch-Site` verification on state-changing routes, or synchronizer or double-submit tokens; require a custom header for JSON APIs. See secure-coding-expert for the general treatment.

## 2. Password policy (NIST SP 800-63B-4)

- Minimum 15 characters if the password is the only authentication factor; 8 if it is one factor within multi-factor authentication. Accept at least 64 characters. Do not truncate silently.
- Allow all printable ASCII, spaces and Unicode; normalize Unicode (NFKC) before hashing. Allow paste and password managers.
- No composition rules (digits, symbols, case) and no scheduled rotation; require a change only on evidence of compromise.
- Reject passwords on a blocklist: breached passwords, dictionary words, repetitive or sequential strings, and values derived from the username or service name.
- Show a strength hint if you like, but enforce length and the blocklist, not a score.
- Never use security questions or password hints.

## 3. Storage

- Argon2id with a unique random salt per password (generated by the library). OWASP Password Storage Cheat Sheet minimum: memory 19 MiB (`memoryCost: 19456` in the `argon2` package, which takes KiB), 2 iterations, 1 lane of parallelism. Treat these as a floor and tune up against your latency budget.
- If Argon2id is not available: scrypt (OWASP minimum includes N=2^17, r=8, p=1) or bcrypt with a work factor chosen from the current cheat sheet; note bcrypt truncates input at 72 bytes, so pre-hash or limit length deliberately. Check the current cheat sheet for exact figures.
- A pepper (secret key applied to every hash, kept outside the database) limits the damage of a database-only leak. Use the library's native `secret` option instead of concatenating strings, version the pepper, and store the version with the hash so rotation is possible.
- Parse hashes as PHC strings (`$argon2id$v=19$m=...,t=...,p=...$salt$hash`); call `needsRehash` on successful login and re-store when parameters are old.
- Legacy hashes (MD5, SHA-1, unsalted): wrap them (store `argon2id(legacyHash)`) and migrate everyone immediately, then replace on next login.

## 4. Breached-password check

The Pwned Passwords range API uses k-anonymity: send the first 5 hex characters of the SHA-1 of the password and compare the returned suffixes locally. The password never leaves your server.

```typescript
import { createHash } from 'node:crypto';

export async function isBreached(password: string): Promise<boolean> {
  const sha1 = createHash('sha1').update(password, 'utf8').digest('hex').toUpperCase();
  const res = await fetch(`https://api.pwnedpasswords.com/range/${sha1.slice(0, 5)}`, {
    headers: { 'Add-Padding': 'true' },          // hides the number of matches from observers
    signal: AbortSignal.timeout(2000),
  });
  if (!res.ok) return false;                      // fail open for availability; log and alert separately
  const suffix = sha1.slice(5);
  return (await res.text()).split('\n').some((line) => line.split(':')[0].trim() === suffix);
}
```

Run it at signup, password change, reset and, because plaintext exists only then, on successful login (prompt a change rather than blocking). SHA-1 here is the API's lookup format, not password storage.

## 5. Login abuse controls

- Rate limit per account identifier and per source IP separately; credential stuffing spreads across accounts, targeted guessing hammers one.
- Backoff or a challenge (proof of work, CAPTCHA, step-up) after repeated failures rather than permanent lockout; return the same generic response while throttled.
- Run the limiter before the hash, so failed attempts cost the attacker more than the server.
- Signup and reset request endpoints must not reveal whether an email is registered: respond "if the address exists, we sent a message" and do the work asynchronously so response time matches.
- Notify users of logins from new devices and of password or factor changes.

## 6. Password reset and account recovery

1. Request: always return the same response. If the account exists, create a random token (32 bytes), store its SHA-256 and expiry (15 to 60 minutes), invalidate earlier tokens, and email a link containing the token in the URL fragment or path.
2. Landing page: do not load third-party resources on the reset page (Referer leak); set `Referrer-Policy: no-referrer`.
3. Submit: look up by the SHA-256 of the presented token, check expiry, validate the new password with the policy and breach check, update the hash, mark the token used, all in one transaction.
4. After reset: revoke all sessions and refresh token families, do not disable MFA as part of a reset, and notify by email.
5. MFA accounts: a reset by email alone must not bypass the second factor. Require the factor, or enforce a waiting period with notifications.
6. Recovery codes: 10 single-use random codes shown once, stored hashed. For passkey-only accounts, offer a second passkey and recovery codes; support-assisted recovery needs identity proofing and an audit trail.
7. Email change: confirm via the new address and notify the old one; delay sensitive changes.

## 7. Tests

- Session id differs before and after login; the pre-login id no longer works.
- Cookie attributes present in `Set-Cookie`: `__Host-` prefix, `HttpOnly`, `Secure`, `SameSite`, `Path=/`, no `Domain`.
- 8-character password rejected when it would be the only factor; 64 and more accepted; composition rules absent; a known breached password rejected.
- Unknown-email reset and registered-email reset return identical bodies and comparable timing.
- Reset token is single use, expires, and stops working when a newer one is requested.
- After password change, other sessions are rejected.
