# Testing NestJS Applications

Reference for unit and end-to-end testing with `@nestjs/testing`, Vitest or Jest, supertest and Fastify `inject`. Verified against NestJS 12.3.2, `@nestjs/testing` 12.3, Vitest 5.0, supertest 7.3, Jest 30 (2026-10); the examples under sections 2 to 5 were executed.

## 1. Choosing the runner

- `@nestjs/testing` is test-runner agnostic. Projects generated by the v12 CLI as ESM use Vitest; CommonJS projects use Jest.
- Nest's decorators need `emitDecoratorMetadata`. Vitest does not emit it with esbuild alone; add an SWC plugin such as `unplugin-swc` to the Vitest config.
- Jest 30 can load the ESM-only v12 packages only on Node.js 24.9 or later (older versions fail with `ERR_REQUIRE_ASYNC_MODULE`). Run the suite on Node 24.9+ or move to Vitest.
- Keep unit tests next to the code (`*.spec.ts`) and e2e tests under `test/` (`*.e2e-spec.ts`), with separate runner configs or scripts.

Vitest configuration for e2e tests:

```ts
// vitest.config.ts
import swc from 'unplugin-swc';
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    include: ['test/**/*.e2e-spec.ts'],
    // ConfigModule.forRoot() runs when AppModule is imported, so set env here, not inside tests
    env: { JWT_SECRET: 'test-secret-test-secret-test-secret-0123' },
  },
  plugins: [swc.vite({ module: { type: 'es6' } })],
});
```

TypeScript settings for ESM projects (as generated by `nest new`): `"module": "nodenext"`, `"moduleResolution": "nodenext"`, `"emitDecoratorMetadata": true`, `"experimentalDecorators": true`, `"isolatedModules": true`, and imports with a `.js` extension.

## 2. Unit tests

Instantiate a provider through the testing module so constructor injection is exercised:

```ts
import { Test } from '@nestjs/testing';
import { beforeEach, describe, expect, it, vi } from 'vitest';
import { UsersController } from './users.controller.js';
import { UsersService } from './users.service.js';

describe('UsersController', () => {
  let controller: UsersController;

  beforeEach(async () => {
    const moduleRef = await Test.createTestingModule({ controllers: [UsersController] })
      .useMocker((token) => {
        if (token === UsersService) {
          return { findOne: vi.fn().mockReturnValue({ id: '1', email: 'a@example.com' }) };
        }
      })
      .compile();
    controller = moduleRef.get(UsersController);
  });

  it('delegates to the service', () => {
    expect(controller.findOne('1')).toEqual({ id: '1', email: 'a@example.com' });
  });
});
```

- `useMocker(factory)` supplies a mock for every missing dependency; return `undefined` to let Nest fail on an unexpected token. `REQUEST` and `INQUIRER` cannot be auto-mocked; replace them with `overrideProvider()` or a custom provider.
- Explicit providers: `providers: [UsersService, { provide: UsersRepository, useValue: fakeRepo }]`.
- `moduleRef.get(Token)` retrieves a singleton; `await moduleRef.resolve(Token)` creates an instance from a request or transient sub-tree; each `resolve()` call returns a different instance unless a context id is passed.
- Test domain logic without Nest where possible (plain classes with constructor arguments); keep Nest-specific tests for wiring, guards and pipes.
- Enhancers can be unit tested directly: build an `ExecutionContext` with a small fake exposing `switchToHttp().getRequest()`, `getHandler()` and `getClass()`, or run them through an e2e test.

## 3. End-to-end tests with supertest

Share the bootstrap configuration with production so the same pipes and prefixes apply:

```ts
// src/configure-app.ts
import { type INestApplication, ValidationPipe } from '@nestjs/common';

export function configureApp(app: INestApplication): void {
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }));
}
```

```ts
// test/users.e2e-spec.ts
import { type INestApplication } from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import { Test } from '@nestjs/testing';
import request from 'supertest';
import { afterAll, beforeAll, describe, expect, it } from 'vitest';
import { AppModule } from '../src/app.module.js';
import { configureApp } from '../src/configure-app.js';

describe('Users (e2e)', () => {
  let app: INestApplication;
  let adminToken: string;

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({ imports: [AppModule] }).compile();
    app = moduleRef.createNestApplication();
    configureApp(app);
    await app.init();
    adminToken = await app.get(JwtService).signAsync({ sub: 'u1', roles: ['admin'] });
  });

  afterAll(async () => {
    await app.close();
  });

  it('rejects anonymous requests', () =>
    request(app.getHttpServer()).post('/users').send({}).expect(401));

  it('rejects unknown properties', () =>
    request(app.getHttpServer())
      .post('/users')
      .set('Authorization', `Bearer ${adminToken}`)
      .send({ email: 'a@example.com', password: 'a-long-password', isAdmin: true })
      .expect(400));

  it('creates and reads a user', async () => {
    const created = await request(app.getHttpServer())
      .post('/users')
      .set('Authorization', `Bearer ${adminToken}`)
      .send({ email: 'a@example.com', password: 'a-long-password' })
      .expect(201);

    await request(app.getHttpServer())
      .get(`/users/${created.body.id}`)
      .set('Authorization', `Bearer ${adminToken}`)
      .expect(200)
      .expect(({ body }) => expect(body.email).toBe('a@example.com'));
  });

  it('forbids a non-admin role', async () => {
    const token = await app.get(JwtService).signAsync({ sub: 'u2', roles: ['user'] });
    await request(app.getHttpServer())
      .post('/users')
      .set('Authorization', `Bearer ${token}`)
      .send({ email: 'b@example.com', password: 'a-long-password' })
      .expect(403);
  });
});
```

Notes:

- Import supertest as a default import (`import request from 'supertest'`).
- Always `await app.close()`; open handles keep the runner alive and leak connections.
- Prefer a real database in a container (or an in-memory substitute with identical behavior) for repository code; mock only outbound third-party services.
- Reset state between tests (transactions rolled back, truncated tables, or a fresh module per suite).
- Do not rely on test order; each test creates its own data.

## 4. Fastify and the Node adapter

Fastify has built-in injection and needs the instance to be ready:

```ts
import { FastifyAdapter, type NestFastifyApplication } from '@nestjs/platform-fastify';

const moduleRef = await Test.createTestingModule({ imports: [AppModule] }).compile();
const app = moduleRef.createNestApplication<NestFastifyApplication>(new FastifyAdapter());
configureApp(app);
await app.init();
await app.getHttpAdapter().getInstance().ready();

const res = await app.inject({ method: 'GET', url: '/users/0b4c1c8e-0000-4000-8000-000000000000' });
expect(res.statusCode).toBe(401);
await app.close();
```

For the `NodeAdapter` (`@nestjs/platform-node`) the supertest approach with `app.getHttpServer()` applies as with Express; confirm behavior differences (route specificity matching, case-sensitive paths) in the HTTP adapters chapter.

## 5. Overriding providers and global enhancers

```ts
const moduleRef = await Test.createTestingModule({ imports: [AppModule] })
  .overrideProvider(MailService)
  .useValue({ send: vi.fn() })
  .compile();
```

A global guard registered as `{ provide: APP_GUARD, useClass: AuthGuard }` cannot be overridden by token. Register it as an existing provider, then override the class:

```ts
providers: [
  { provide: APP_GUARD, useExisting: AuthGuard }, // not useClass
  AuthGuard,
],
```

```ts
const moduleRef = await Test.createTestingModule({ imports: [AppModule] })
  .overrideProvider(AuthGuard)
  .useClass(AllowAllGuard)
  .compile();
```

The same technique applies to `APP_PIPE`, `APP_INTERCEPTOR` and `APP_FILTER`. Other overrides: `overrideGuard()`, `overrideInterceptor()`, `overridePipe()`, `overrideFilter()` for enhancers bound with decorators; `overrideModule()` to replace a whole module.

## 6. Request-scoped providers

`moduleRef.get()` fails for request-scoped providers because their sub-tree is created per request. Generate a context id and force Nest to use it:

```ts
import { ContextIdFactory } from '@nestjs/core';

const contextId = ContextIdFactory.create();
vi.spyOn(ContextIdFactory, 'getByRequest').mockImplementation(() => contextId);
const service = await moduleRef.resolve(RequestScopedService, contextId);
```

## 7. Testing guards, pipes and filters

- Guards: e2e tests assert 401 and 403 for routes; unit tests can call `canActivate()` with a mocked `ExecutionContext` and a `Reflector` configured through `Test.createTestingModule`.
- Pipes: instantiate and call `transform(value, { type: 'body', metatype: CreateUserDto })`. For `ValidationPipe`, assert that the thrown `BadRequestException` response contains the expected messages (`errorFormat: 'list'` returns an array of strings, `'grouped'` groups by property).
- Filters: use an e2e request that triggers the exception and assert status and body shape; unit test mapping functions separately.
- Interceptors: call `intercept(context, { handle: () => of(value) })` and assert on the emitted value with `firstValueFrom`.

## 8. Microservices and messaging

- Unit test `@MessagePattern` and `@EventPattern` handlers as plain methods with their payload arguments.
- For wiring tests, create the application with `createNestMicroservice` or a hybrid app against the real transport running in a container, and use `ClientProxy` with `firstValueFrom(client.send(pattern, data))`.
- Keep timeouts short in tests and close clients in `afterAll`.

## 9. What to verify

- Validation: missing field, wrong type, unknown property (400), boundary values.
- Authentication and authorization: no token (401), expired or tampered token (401), wrong role (403), another user's resource (403 or 404 per policy), another tenant's resource on read and on write.
- Error format: stable machine-readable `errorCode` where used, no stack traces in bodies.
- Shutdown: `app.close()` runs `onApplicationShutdown` hooks; connections are released.
- Configuration: the app fails fast when a required variable is missing or invalid.
