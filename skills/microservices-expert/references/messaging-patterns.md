# Messaging Patterns

Reference for reliable asynchronous communication between services: delivery guarantees, the transactional outbox (polling and change-data-capture), inbox and idempotency keys, ordering, dead-letter handling, sagas, event schema evolution, and the API gateway and BFF edge. Verified against Apache Kafka producer defaults (`enable.idempotence=true`), the Debezium outbox event router, CloudEvents 1.0 and PostgreSQL 16+ SQL (2026-10). Examples use TypeScript and PostgreSQL; the patterns apply to any broker.

## 1. Delivery guarantees

- Brokers and networks fail between "message sent" and "ack received", so a producer retries and a consumer may see a message more than once. Design for at-least-once delivery plus idempotent processing; the combination behaves like exactly-once for the business effect.
- Kafka idempotent producers (default on in current clients) remove duplicates caused by producer retries within one producer session. Kafka transactions make a consume-transform-produce loop atomic between Kafka topics. Neither makes a database write and a Kafka publish atomic; that is what the outbox is for.
- Commit the consumer offset (or acknowledge the queue message) only after the side effect is durable. If the side effect and the offset live in different systems, the side effect must be idempotent.
- A command that must be applied once needs an idempotency key chosen by the caller (a UUID per intended action) and stored by the receiver with the result.

## 2. Transactional outbox

Write the business change and an event row in one local transaction. A separate process publishes the row. If the process crashes after publishing but before marking the row, the event is published again, which is why consumers must be idempotent.

### Polling relay

- Query unpublished rows with `FOR UPDATE SKIP LOCKED`, publish, mark published, commit. A worker crash rolls back the lock and another worker retries.
- Ordering: rows commit in a different order than their `created_at` or sequence values, and multiple workers interleave. If consumers need per-aggregate order, run a single relay per outbox partition (for example `hashtext(aggregate_id) % N`), or use CDC.
- Add a partial index on unpublished rows and delete or archive published rows on a schedule. Monitor `now() - min(created_at)` for unpublished rows as the relay lag.
- The full table and relay code is in the main SKILL.md examples.

### CDC relay with Debezium

The connector reads the database log and the outbox event router transformation turns inserted outbox rows into broker messages. Default columns are `id`, `aggregatetype`, `aggregateid`, `type`, `payload`; the options below map custom column names. The router only processes inserts, so a common pattern is to insert and delete the row in the same transaction (the insert is still in the log) or to clean up with a scheduled job.

```properties
# Kafka Connect connector properties (excerpt)
connector.class=io.debezium.connector.postgresql.PostgresConnector
table.include.list=public.outbox
transforms=outbox
transforms.outbox.type=io.debezium.transforms.outbox.EventRouter
transforms.outbox.route.by.field=aggregate_type
transforms.outbox.route.topic.replacement=outbox.event.${routedByValue}
transforms.outbox.table.field.event.key=aggregate_id
transforms.outbox.table.fields.additional.placement=type:header:eventType,tenant_id:header:tenantid,traceparent:header:traceparent
transforms.outbox.table.expand.json.payload=true
value.converter=org.apache.kafka.connect.json.JsonConverter
```

Check the Debezium documentation for the properties of your connector version (database connection and credentials come from a secret provider, not from the properties file in version control).

## 3. Inbox and idempotent consumers

| Technique | When to use |
|---|---|
| Inbox table (`tenant_id, consumer, message_id` primary key) inserted in the same transaction as the effect | General case; works for any effect that is a database write |
| Natural idempotency (set status to `PAID` where status is `PENDING`; upsert by key) | The effect is already a state assertion |
| Version or sequence check (`WHERE version = $expected`) | Aggregates with optimistic concurrency; also rejects stale or reordered events |
| Idempotency key on commands (`Idempotency-Key` header stored with the response) | HTTP or queue commands that create things (payments, orders) |

- Include the tenant in every dedupe key; two tenants may legitimately reuse an id.
- Store the result with the idempotency key and return it for repeats, so a retried request gets the original response.
- Expire inbox rows after the broker retention window plus a safety margin; an unbounded inbox is a slow leak.
- Message ids must come from the producer (outbox row id), never be generated by the consumer on receipt.

## 4. Ordering and partitioning

- Ordering is only guaranteed within a partition (Kafka) or message group/FIFO group (SQS FIFO and similar). Choose the key as the aggregate id, prefixed by tenant id (`tenantId:orderId`).
- Consumers of the same partition process sequentially; to raise throughput without losing key order, increase partitions rather than adding in-process concurrency over the same key.
- Handle out-of-order and duplicate events with versions: ignore events whose version is not greater than the stored one, and park events with a gap until the missing one arrives or a timeout expires.
- Do not rely on global ordering across topics. If a workflow needs two facts, include both in one event or correlate by a saga id.

## 5. Dead-letter queues and replay

- Distinguish transient errors (retry with backoff, then delay queues) from permanent errors (schema violation, unknown version, business rule failure): permanent errors go to the DLQ immediately with the reason, original headers, and attempt count.
- A poison message must not block the partition: after N attempts, publish to `<topic>.dlq` and continue.
- Keep a replay tool that republishes DLQ messages to the original topic after a fix; replay relies on idempotent consumers.
- Alert on DLQ depth and on the age of the oldest DLQ message. Apply the same access controls as the source topic; DLQs contain the same sensitive data.

## 6. Sagas

A saga is a sequence of local transactions across services. Each step has a compensating action that semantically undoes it. There is no isolation between steps, so intermediate states are visible; design for that (for example, an order is `PENDING` until confirmed, and stock is `RESERVED` before it is `SOLD`).

### Choreography

Services react to each other's events: `order.placed` triggers stock reservation, which emits `stock.reserved`, which triggers payment. Good for two or three participants. It becomes hard to follow beyond that because the flow lives in subscriptions spread across services. Add a correlation id (saga id) on every event and a read model that reconstructs progress.

### Orchestration

One coordinator owns the state machine. It sends commands and consumes replies. Progress, timeouts and compensation are visible in one place. The orchestrator contains sequencing only; business rules stay in the participant services.

```ts
// Saga state is a row; every transition is a conditional update inside the same
// transaction that writes the next command to the outbox. Tenant is in every predicate.
interface Tx { query<T = unknown>(sql: string, params?: unknown[]): Promise<{ rows: T[] }> } // a pg client inside BEGIN/COMMIT

type Step = "RESERVE_STOCK" | "CAPTURE_PAYMENT" | "COMPLETED" | "COMPENSATING" | "FAILED";

interface SagaRow { id: string; tenant_id: string; order_id: string; step: Step; deadline_at: Date }

// Called for each reply message (already deduplicated through the inbox).
export async function onReply(tx: Tx, tenantId: string, sagaId: string, reply: "stock.reserved" | "stock.rejected" | "payment.captured" | "payment.declined" | "stock.released") {
  const { rows } = await tx.query<SagaRow>(
    "SELECT id, tenant_id, order_id, step, deadline_at FROM sagas WHERE id = $1 AND tenant_id = $2 FOR UPDATE",
    [sagaId, tenantId],
  );
  const s = rows[0];
  if (!s) return;                                   // unknown or other tenant's saga: ignore

  const next = transition(s.step, reply);           // pure function, unit-testable
  if (!next) return;                                // reply not valid in this state: duplicate or late

  await tx.query(
    "UPDATE sagas SET step = $3, deadline_at = now() + interval '2 minutes' WHERE id = $1 AND tenant_id = $2 AND step = $4",
    [s.id, s.tenant_id, next.step, s.step],
  );
  for (const cmd of next.commands) {
    await tx.query(
      `INSERT INTO outbox (id, tenant_id, aggregate_type, aggregate_id, type, payload)
       VALUES (gen_random_uuid(), $1, 'saga', $2, $3, $4)`,
      [s.tenant_id, s.id, cmd.type, JSON.stringify({ sagaId: s.id, orderId: s.order_id, ...cmd.data })],
    );
  }
}

function transition(step: Step, reply: string): { step: Step; commands: { type: string; data?: object }[] } | null {
  switch (`${step}:${reply}`) {
    case "RESERVE_STOCK:stock.reserved":   return { step: "CAPTURE_PAYMENT", commands: [{ type: "payment.capture.v1" }] };
    case "RESERVE_STOCK:stock.rejected":   return { step: "FAILED", commands: [{ type: "order.cancel.v1" }] };
    case "CAPTURE_PAYMENT:payment.captured": return { step: "COMPLETED", commands: [{ type: "order.confirm.v1" }] };
    case "CAPTURE_PAYMENT:payment.declined": return { step: "COMPENSATING", commands: [{ type: "stock.release.v1" }] };
    case "COMPENSATING:stock.released":    return { step: "FAILED", commands: [{ type: "order.cancel.v1" }] };
    default: return null;
  }
}
```

- A scheduled job selects sagas past `deadline_at` in a non-terminal step and either re-sends the command (commands are idempotent) or starts compensation.
- Compensations must be retryable and idempotent. A compensation that can fail permanently needs a manual-intervention state and an alert.
- Step commands carry the saga id so replies correlate; participants return the saga id unchanged.
- Use a workflow engine (Temporal, Camunda, AWS Step Functions) when sagas are long-running, need human tasks, or have many branches; the same principles apply.

## 7. Event schema evolution

- Treat an event schema as a public API. The producer may not know all consumers.
- Compatible changes: add an optional field, add a new enum value only if consumers have a safe default, widen a numeric range. Incompatible: rename or remove a field, change type, unit or meaning, make an optional field required.
- Consumers are tolerant readers: ignore unknown fields, apply defaults for missing optional ones, and route unknown event versions to a DLQ.
- Version in the type name (`order.placed.v1`) or in a `dataschema` URI; a breaking change publishes a new type (`v2`), usually alongside `v1` during a migration window, then retires `v1` when metrics show no consumers.
- Enforce compatibility in CI: a schema registry compatibility mode (backward, forward or full, chosen per topic), or contract tests that every consumer runs against the producer's example messages.
- Protobuf and Avro: never reuse a removed field number or name; give new fields defaults. JSON: validate with JSON Schema and set `additionalProperties` deliberately (allow on consumers that read, forbid when strictness is part of the contract).
- Upcasting: a consumer or an ingest step converts old versions to the current internal model, so business code handles one shape.
- Keep PII out of event payloads when an id and a callback would do; events are retained and replicated.

## 8. API gateway and BFF

- Gateway responsibilities: TLS termination, authentication (token validation), coarse authorization, rate limiting and quotas, request size limits, routing, request id and trace context creation, response caching of public data. Not responsibilities: business rules, data joins, orchestration of sagas.
- Internal services still validate tokens and authorize; the gateway is not the only line of defense.
- A BFF is owned by the team that owns the client experience. It composes calls (in parallel, with deadlines), shapes payloads, and handles partial failure with explicit degraded fields. Do not let BFFs call each other.
- GraphQL or REST at the edge is a client concern; between services prefer typed contracts (gRPC/protobuf or OpenAPI) with generated clients.
- Keep gateway configuration in version control, test routes in CI, and give each upstream its own timeout, retry policy (usually none for non-idempotent routes) and circuit breaker.
