## 1. CLI commands

| Command | Purpose |
|---|---|
| `npx ng new my-app` | Create a workspace (prompts for SSR and options) |
| `npx ng serve` | Dev server with live reload (esbuild and Vite) |
| `npx ng generate component orders/order-list` | Scaffold a component (aliases: `g`, `c`) |
| `npx ng generate service orders/orders-api` | Scaffold a service (`@Service` in v22 workspaces) |
| `npx ng build` | Production build into `dist/<project>/` |
| `npx ng test --no-watch` | Run unit tests once |
| `npx ng add @angular/material` | Add a package and run its install schematic |
| `npx ng update` | List available updates; `ng update @angular/core @angular/cli` applies them |
| `npx ng version` | Show CLI, framework, Node and TypeScript versions |
| `npx ng build --stats-json` | Emit stats for a bundle analyser |

- `ng generate --help` and `ng generate component --help` list the options for the installed CLI; options such as `--inline-template`, `--skip-tests` and `--change-detection` exist on component generation (check `--help` for the current set).
- In v22 workspaces, generated components default to `OnPush` and `ng generate service` uses the service decorator.
- Node requirement for CLI 22.2.5: `^22.22.3 || ^24.15.0 || >=26.0.0` (`npm view @angular/cli engines`). Node 20 is unsupported since v22.
- Port selection: from v22 the `PORT` environment variable takes priority over `angular.json` and `--port` for `ng serve`.

## 2. ng new defaults

The application schematic schema in CLI 22 (angular-cli repository) sets these defaults:

| Option | Default | Notes |
|---|---|---|
| `standalone` | `true` | NgModule-based apps are legacy |
| `zoneless` | `true` | No Zone.js in new apps |
| `routing` | `true` | Generates `app.routes.ts` |
| `style` | `css` | `scss`, `sass`, `less`, `tailwind` are available |
| `ssr` | `false` | `--ssr` adds `@angular/ssr`, a server file and server routes |
| `testRunner` | `vitest` | `karma` is the alternative |
| `prefix` | `app` | Selector prefix |
| `skipTests` | `false` | Generates `.spec.ts` files |

```bash
npx ng new storefront --style=scss --ssr --test-runner=vitest
```

- `--file-name-style-guide` chooses between suffixless names (`order-list.ts`) and the older `.component.ts` style; the CLI prompts or uses its default.
- Add AI-assistant config files with the `ai-config` schematic only if the team wants them (it supports an `AGENTS.md` file).
- Pin the package manager through the `packageManager` field that new projects receive.

## 3. Builders and configuration

- The `@angular/build` package provides the builders: `application` (browser, optional server and prerender), `dev-server`, `unit-test`, `extract-i18n`. Webpack builders from `@angular-devkit/build-angular` are deprecated in v22; the experimental Jest and Web Test Runner builders were removed.
- Key `application` options: `browser` (entry), `server`, `ssr`, `outputMode` (`static` or `server`), `polyfills`, `assets`, `styles`, `budgets`, `optimization`, `sourceMap`, `security.autoCsp`, `allowedCommonJsDependencies`.
- Use file replacements or tokens for environment differences rather than branching on `isDevMode()` everywhere.
- Strictness: keep `"strict": true`, `strictTemplates` (generated by default in v22), `noImplicitOverride` and `noPropertyAccessFromIndexSignature` in `tsconfig.json`. The compiler requires TypeScript 6.0.x for Angular 22.2.4.
- `ng build --configuration development` produces unminified output for debugging; production is the default configuration.

## 4. Server-side rendering

```ts
// app.routes.server.ts
import {RenderMode, ServerRoute} from '@angular/ssr';

export const serverRoutes: ServerRoute[] = [
  { path: '', renderMode: RenderMode.Prerender },
  { path: 'products/:id', renderMode: RenderMode.Prerender,
    async getPrerenderParams() { return [{ id: '1' }, { id: '2' }]; } },
  { path: 'account/**', renderMode: RenderMode.Client },
  { path: '**', renderMode: RenderMode.Server },
];
```

```ts
// app.config.server.ts
import {mergeApplicationConfig, ApplicationConfig} from '@angular/core';
import {provideServerRendering, withRoutes} from '@angular/ssr';
import {appConfig} from './app.config';
import {serverRoutes} from './app.routes.server';

export const config = mergeApplicationConfig(appConfig, {
  providers: [provideServerRendering(withRoutes(serverRoutes))],
});
```

- Render modes: `Prerender` (build-time HTML), `Server` (per request), `Client` (no server HTML). Per-route modes allow a hybrid site; set `outputMode: "static"` for a fully static deployment.
- `AngularNodeAppEngine` or `AngularAppEngine` handle requests; `CommonEngine` APIs are deprecated in CLI 22.
- v22 returns HTTP 400 for requests whose `Host` header is not recognised, instead of falling back to client rendering. Configure the allowed hosts for each deployment (check the SSR documentation) and run the trusted-proxy migration if you sit behind a proxy.
- Browser-only APIs (`window`, `localStorage`, `IntersectionObserver`) are unavailable on the server. Guard with `isPlatformBrowser(inject(PLATFORM_ID))`, or put the code in `afterNextRender`.
- The server uses fetch for HTTP; relative URLs resolve against the request origin. v22 limits the buffered size of fetch responses on SSR.
- In v22, `platform-server` throws on suspicious URLs and restricts protocol-relative URLs (security hardening backported to 19.2.x, 20.3.x and 21.2.x); keep patch versions current.
- Do not render user-specific data into prerendered pages; prerendered HTML is public and cached.
- Delay serialisation of the server render until async work finishes by registering `PendingTasks` or using `pendingUntilEvent`.

## 5. Hydration

```ts
import {provideClientHydration} from '@angular/platform-browser';

providers: [provideClientHydration()]    // v22: incremental hydration and event replay are on by default
```

```html
@defer (hydrate on interaction) {
  <app-reviews [productId]="id()" />
} @placeholder {
  <div style="min-height: 240px"></div>
}
```

- Hydration reuses server DOM instead of re-creating it. Direct DOM manipulation (`innerHTML`, `appendChild` on Angular-owned nodes) can cause mismatch errors; keep DOM edits inside `afterNextRender` or use `ngSkipHydration` on the host only as a last resort.
- Incremental hydration: `hydrate on idle | viewport | interaction | hover | immediate | timer(...)`, `hydrate when expr`, `hydrate never`. Parents hydrate before children. Before v22 it required `withIncrementalHydration()`; in v22 `provideClientHydration()` enables it (`withIncrementalHydration` and `withEventReplay` are still exported; check the current docs before removing them).
- The HTTP transfer cache stores server responses in the page so the browser does not repeat them; `transferCache` can be controlled per request or with `withHttpTransferCacheOptions`.
- Check the browser console for hydration mismatch errors after each change to templates that render differently on server and client (dates, random ids, locale).

## 6. Testing with Vitest

New projects run `ng test` through the `unit-test` builder with Vitest and jsdom; `happy-dom` is the supported alternative DOM. `describe`, `it` and `expect` are available as globals in CLI-generated specs.

```ts
import {TestBed} from '@angular/core/testing';
import {Rating} from './rating';

describe('Rating', () => {
  it('emits the picked value', async () => {
    const fixture = TestBed.createComponent(Rating);
    fixture.componentRef.setInput('label', 'Quality');
    await fixture.whenStable();

    const rated: number[] = [];
    fixture.componentInstance.rated.subscribe(v => rated.push(v));
    fixture.nativeElement.querySelectorAll('button')[2].click();

    expect(rated).toEqual([3]);
  });
});
```

```ts
it('redirects anonymous users', () => {
  TestBed.configureTestingModule({ providers: [{ provide: AuthService, useValue: { isLoggedIn: () => false } }] });
  const result = TestBed.runInInjectionContext(() => requireLogin({} as any, {} as any));
  expect(result.toString()).toBe('/login');
});
```

- Options live on the `test` target in `angular.json` (`include`, `exclude`, `coverage`, `browsers`, `runnerConfig`). Generate a base Vitest config with `ng generate config vitest` for advanced setups.
- Browser mode needs a provider package such as `@vitest/browser-playwright` plus `playwright`; follow the Vitest browser guide.
- Zoneless tests: set inputs with `fixture.componentRef.setInput`, then `await fixture.whenStable()`. v22 adds `TestBed.getLastFixture()`; `ChangeDetectorRef.checkNoChanges` was removed (use `fixture.detectChanges()`). `TestBed.tick()` flushes pending effects.
- Fake timers: use Vitest's `vi.useFakeTimers()` rather than Zone.js `fakeAsync`; the migration schematics convert `fakeAsync` usage.
- Migrate from Karma and Jasmine: `ng update` includes a Karma-to-Vitest migration in v22, and the `refactor-jasmine-vitest` schematic rewrites spec syntax (spies, matchers, `done` callbacks). Review the diff and run the suite; some spy semantics differ.
- Karma remains supported (`--test-runner=karma`) for projects that are not ready.
- Keep tests deterministic: no real network, no real timers beyond fakes, no reliance on test order.
- Component harnesses from `@angular/cdk/testing` (`TestbedHarnessEnvironment`) are the stable way to drive Material components.

## 7. Upgrading

1. Commit a clean tree and make sure tests pass.
2. Check `npx ng update` output and the update guide at https://angular.dev/update-guide for the from and to versions.
3. Update one major at a time: `npx ng update @angular/core@22 @angular/cli@22`. Update `@angular/material`, `@angular/cdk` and `@ngrx/*` to the matching major in the same step or immediately after.
4. Raise Node and TypeScript to the supported ranges first (Angular 22.2.4 needs TypeScript 6.0.x and rxjs 6.5.3+ or 7.4+; zone.js, if still used, `~0.15.0 || ~0.16.0`).
5. Review the automatic migrations in the diff. Known v22 effects: `ChangeDetectionStrategy.Eager` added where components relied on the old default, `strictTemplates` added to tsconfig, two new template diagnostics temporarily disabled, `withXhr()` added where upload progress was used, `CanMatchFn` signature updated, `paramsInheritanceStrategy` behaviour change.
6. Optional modernisation schematics: control flow, `inject()`, signal inputs, outputs and queries, standalone, `@Injectable` to `@Service` (list them with `npx ng generate @angular/core:` and read each migration's `--help`).
7. Build, run tests, run the app and check the console; then commit.

## 8. Budgets, images and accessibility

```json
"budgets": [
  { "type": "initial", "maximumWarning": "500kB", "maximumError": "1MB" },
  { "type": "anyComponentStyle", "maximumWarning": "4kB", "maximumError": "8kB" }
]
```

- Tune the numbers from a measured baseline; fail CI on errors.
- `NgOptimizedImage`: `import {NgOptimizedImage} from '@angular/common'`, then `<img ngSrc="hero.jpg" width="800" height="450" priority alt="Product on a desk">`. Use `fill` for responsive containers, `priority` for the largest contentful image only, and an image loader (`provideImgixLoader`, `provideCloudflareLoader`, others) for a CDN.
- Accessibility: use native elements (`button`, `a`, `label`), keep focus visible, move focus to the main heading after route changes, use `aria-live` regions for async status, and test with the Angular CDK `a11y` utilities (`FocusTrap`, `LiveAnnouncer`, `FocusMonitor`) and axe in CI. Material components follow ARIA patterns but your labels and content still need review.
- Core Web Vitals work belongs to core-web-vitals-expert; broader accessibility audits to accessibility-expert.

## 9. Material, CDK and NgRx Signal Store

- Angular Material (`@angular/material`, 22.2.5 on npm) provides Material Design components with theming; install with `ng add @angular/material`. Import standalone components individually (`MatButton`, `MatDialog` provider usage). The CDK (`@angular/cdk`) has behaviour primitives: overlay, drag-drop, virtual scroll, a11y, clipboard, table, testing harnesses. Check the Material site for the current theming API before writing theme code.
- Prefer harnesses in tests and avoid selecting Material internals by class name.
- NgRx Signal Store (`@ngrx/signals` 22.0.1, peer `@angular/core ^22.0.0`):

```ts
import {computed} from '@angular/core';
import {patchState, signalStore, withComputed, withMethods, withState} from '@ngrx/signals';

interface CartState { lines: { sku: string; qty: number }[] }

export const CartStore = signalStore(
  { providedIn: 'root' },
  withState<CartState>({ lines: [] }),
  withComputed(({ lines }) => ({ count: computed(() => lines().reduce((n, l) => n + l.qty, 0)) })),
  withMethods((store) => ({
    add(sku: string) { patchState(store, (s) => ({ lines: [...s.lines, { sku, qty: 1 }] })); },
  })),
);
```

- Inject with `inject(CartStore)`. Use it when several features share structured state, need entities, plugins or DevTools; a plain signal service is enough for simple cases.
